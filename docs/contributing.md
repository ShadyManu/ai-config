# Contributing

## Requirements

- Node.js 20.10 or later
- pnpm 11

## Getting started

```bash
pnpm install
pnpm build
pnpm test
```

## Quality gates

All of these must pass before a change is complete:

```bash
pnpm install
pnpm format:check # Prettier
pnpm typecheck    # tsc -b for sources, plus the test project
pnpm lint
pnpm test         # core, adapters, CLI
pnpm build
pnpm test:vscode  # extension tests, in a real Extension Development Host
```

`pnpm typecheck` covers test files as well as sources. Tests are typechecked as
ES modules through `tsconfig.test.json`, because that is how Vitest loads them.

## Formatting

Prettier owns formatting; run `pnpm format` to apply it. ESLint enforces
correctness only — `eslint-config-prettier` turns off anything stylistic, so the
two can never disagree.

Three things are deliberately outside Prettier's reach, listed in
`.prettierignore`:

- **Markdown**, which is hand-wrapped, and whose code samples are aligned for
  readability rather than by a formatter.
- **`packages/*/test/fixtures/`**, the byte-exact expected provider output.
  Reformatting a fixture silently changes what the test claims an adapter emits.
- **`examples/`**, the input side of that same contract. Its content is embedded
  verbatim in generated files.

The working tree is LF everywhere, including on Windows, enforced by
`.gitattributes`. Generated output must not depend on the platform's checkout
conversion.

## Repository layout

```text
apps/vscode/            VS Code extension
packages/core/          domain model, parser, validator, sync engine
packages/agents-md/     shared AGENTS.md renderer (Codex + OpenCode)
packages/adapter-*/     one package per provider
packages/providers/     composition root: the built-in adapter set
packages/cli/           the aiconfig command
docs/                   specification, architecture, provider research
examples/basic/         a worked example, used as the test fixture input
```

[docs/architecture.md](architecture.md) explains the pipeline and why the
boundaries sit where they do. Read it before changing anything structural.

## Import boundaries

The architecture is enforced by ESLint, not by convention:

- `@aiconfig/core` may not import `vscode` or any adapter.
- An adapter may not import another adapter, `node:fs` or `node:path`.
- Only `apps/vscode` may import `vscode`.

If a rule is in your way, the design is probably wrong — not the rule.

## Testing

| Layer | Location | Purpose |
| --- | --- | --- |
| Unit | `packages/core/test` | parsing, validation, path safety, planner |
| Fixture | `packages/adapter-*/test` | exact generated bytes per provider |
| Cross-provider | `packages/providers/test` | every provider combination, every override field |
| Integration | `packages/core/test/integration` | real filesystem, temp directories |
| End-to-end | `packages/cli/test` | CLI commands against a temp copy of the example |
| Extension | `apps/vscode/src/test` | activation and command registration |

Tests must be deterministic and independent: no network, no reliance on the
developer's real Claude, Codex, Copilot or OpenCode configuration, no shared
mutable state, and no sleeps. Unit tests use the in-memory `FileSystem`;
anything touching real files uses a temporary directory and cleans up.

Nothing writes into `examples/basic`. End-to-end tests copy it first.

### Golden fixtures

Provider output is a serialization contract, so adapter tests compare the
**complete** generated tree against checked-in expected files.

To update them after an intentional change:

```bash
UPDATE_FIXTURES=1 pnpm test
```

Then review the diff. A fixture change is a change to what every user's
repository will contain — it deserves the same scrutiny as the code.

### Combination tests

A fixture test compiles one adapter against one repository. The guarantees that
only hold *across* providers are covered in `packages/providers/test`, which
enumerates rather than samples: all sixteen enabled-provider subsets, all 256
transitions between them, the generated path and capability of every artifact
kind on every provider, and every field of every declared override schema.

The expected generated paths, the capability of each mapping, and the
provider-and-kind override grid are all typed `Record<ProviderId, …>`, so adding
a provider stops the test project compiling until each is filled in. The
remaining declarations — the shared skill roots in `INTAKES`, the co-owners of
`AGENTS.md`, the per-provider override files the lifecycle matrix seeds — are
plain values, and a missing entry fails as an assertion instead. Both are
deliberate: a new provider should not be able to join the set without stating
what it generates, what it reads, and what it accepts.

The override sweep is driven entirely by each adapter's `overrides`
declaration, so a field added there is covered immediately, and a field
declared with a type it cannot actually carry fails there rather than in a
user's repository.

## Adding a provider

1. **Research first.** Read the provider's current official documentation and
   write `docs/providers/<name>.md`, quoting the exact paths and frontmatter
   fields. Do not rely on memory; provider behaviour changes often.
2. Add a row to `docs/provider-capabilities.md`. Classify each canonical
   capability as `native`, `converted`, `partial` or `unsupported`, and explain
   every non-native mapping. `unsupported` is a valid answer — inventing a
   mapping to fill the table is not.
3. Add the identifier to `ProviderId` in `packages/core/src/domain/provider.ts`.
4. Create `packages/adapter-<name>/` implementing `ProviderAdapter`.
5. **Record any location the provider reads but does not own** in the adapter's
   `alsoReads`. Several providers scan another provider's skills directory, or
   read a shared `AGENTS.md`. If the new provider does, declare it: an adapter
   cannot see which other providers are enabled, so this declaration is the
   only way that overlap gets reported instead of silently emitted.
6. **Declare every location the adapter may generate into** in `targetRoots`,
   as narrowly as the provider allows — `.github/agents`, never `.github`. It is
   how Initialize recognizes pre-existing provider files, and a test fails if
   the adapter writes outside what it declares.
7. Add one line to `packages/providers/src/index.ts`.
8. Add fixture tests and generate the expected tree.
9. Extend the combination tests in `packages/providers/test`. The typed tables
   stop the test project compiling until the new provider is listed; the plain
   declarations — shared skill roots, `AGENTS.md` co-owners, the override files
   the lifecycle matrix seeds — fail as assertions instead.

No change to the synchronization engine should be needed. If one is, say so in
the pull request — it means the adapter contract is missing something.

## Design rules

These come from hard constraints, not taste:

- **`.ai/` is the source of truth.** Provider configuration is never read back
  into it automatically, and a synchronization never creates or modifies a file
  there. It removes exactly one: an override whose canonical artifact is gone,
  which no longer refines anything and which nothing can create in that state.
- **Never touch a file AI Config does not own.** The manifest is the only
  authority for overwriting and deleting.
- **Compilation is pure.** Adapters take the IR and return artifacts; they
  perform no I/O, read no clock, and generate no randomness. That is what makes
  `--dry-run` provably side-effect free.
- **Output is deterministic.** Same input, same bytes, on every platform and
  in every locale. Never sort with `localeCompare`.
- **Never silently discard configuration.** Unknown frontmatter fields are
  errors; lossy provider mappings emit warnings.
- **No LLM, no network, no telemetry, no accounts.**

## Diagnostics

Every user-facing problem is a `Diagnostic` with a stable machine-readable
code, declared in `packages/core/src/domain/codes.ts`. Adding a code means
adding it there — `Diagnostic.code` is a checked union, not a free-form string.

Messages should say what is wrong *and* what to do about it:

```text
UNTRACKED_TARGET_EXISTS
AGENTS.md
'AGENTS.md' already exists and was not created by AI Config, so it will not be
overwritten. Move its content into '.ai/' and delete the file, then run sync
again.
```

## Debugging the extension

Open the repository root in VS Code and press <kbd>F5</kbd>. This builds the
workspace, bundles the extension, and launches an Extension Development Host.

Open a folder containing a `.ai/` directory in that window — `examples/basic`
works. The **AI Config** output channel logs every load, sync and write.

## Pull requests

- Keep the change focused; mention unrelated problems separately rather than
  fixing them in passing.
- Update the specification when you change canonical behaviour, and the
  provider research notes when you change a mapping.
- Do not commit generated provider files for this repository itself.

## Releasing

The CLI and the extension go out to different registries but carry **one version
number**. A successful release is recorded by the automated `vX.Y.Z` tag.

They are versioned in lockstep because each bundles its own copy of the same
compiler — neither resolves it at runtime. Two versions installed against one
repository would emit different files from the same `.ai/`, and each would then
read the other's output as drift. The shared number is the only thing that says
which compiler a user is running, so it has to mean the same in both places.

The cost is a Marketplace release for a change that only touched the CLI, and
the reverse. That is cheap; a silent compiler mismatch in a user's repository is
not.

A published npm version is immutable. It cannot be corrected, only replaced by a
higher one, so the tests below run before publishing rather than after.

### `@aiconfig/cli`

The release version is declared in the workspace manifest, both published
manifests, and as `VERSION` in the CLI source. Set all four with:

```sh
pnpm version:release X.Y.Z
```

Then add a `## [X.Y.Z]` section to both public changelogs. The release tests fail
if any declaration disagrees or either changelog has no section for the version
being shipped.

Push the release through a pull request. CI runs formatting, typechecking,
linting, unit tests, extension integration tests, the dependency audit, and both
packagers. Repeated fixes on the release branch publish nothing.

Merging the pull request into `main` starts `.github/workflows/release.yml`. It
validates that all manifests agree and checks for the matching `vX.Y.Z` tag. If
the tag already exists, there is nothing to publish. Otherwise it rebuilds and
tests the exact commit on `main`, creates the CLI tarball and VSIX once, then
publishes those immutable artifacts in separate jobs to npm, the Visual Studio
Marketplace and Open VSX. The tag is created automatically only after every
registry succeeds.

Publishing is idempotent: npm is queried for the exact package version, while
both extension registries skip an existing version. If a registry fails, rerun
the failed workflow without changing the version; the completed registries are
skipped and the missing publication is retried.

Verify against the registries rather than the working tree, since that is what
a user gets:

```sh
npx @aiconfig/cli@latest --version
```

A broken version can be removed within 72 hours with `npm unpublish`; that
version number is then permanently unusable. After 72 hours it can only be
marked with `npm deprecate` and superseded.

### The extension

`pnpm version:release` has already updated `apps/vscode/package.json` to match
the CLI. After documenting the release in `apps/vscode/CHANGELOG.md`, build and
install the artifact locally before tagging:

```sh
pnpm package
code --install-extension ai-config.vsix --force
```

`--force` matters when reinstalling the same version number: without it the
files are replaced but the running extension host keeps the old code, and the
build appears not to have changed. `--packagePath` publishes the file that was
just tested rather than building an untested one.

### Open VSX

Open VSX distributes the same VSIX to compatible editors such as Google
Antigravity and Windsurf. Create the `aiconfig` namespace once and save its
access token as the GitHub Actions secret `OVSX_PAT`. Save the Visual Studio
Marketplace token as `VSCE_PAT`. npm uses trusted publishing through GitHub
OIDC, so it needs no long-lived npm token.

```sh
npx ovsx create-namespace aiconfig # first release only
```

Configure npm's trusted publisher for repository `ShadyManu/ai-config` and
workflow filename `release.yml`. Registry credentials are available only to the
workflow triggered by a push to `main`; pull requests cannot publish.
